# v0.15 SQLite 单机部署决定

日期：2026-11-17。用户要求部署简单、容易维护、避免大型架构组件，并明确要求将 SQLite 改造作为功能分支，通过 PR 交付。本决定替代 v0.13/v0.14 的 PostgreSQL 与多实例部署选择。

## 运行目标

一个 Node.js 服务进程连接本机 SQLite 数据库，浏览器仍通过 HTTP API 访问。保留多账号、多家庭和原业务界面；默认启动不需要 Docker、PostgreSQL、数据库账号或数据库端口。只维护 SQLite 一套存储实现，不引入 ORM、双后端兼容层或分布式组件。

使用 Node >=22.17 的内置 `node:sqlite`，无需原生 npm 插件编译或下载数据库二进制。Node 22 会显示该模块的实验性 API 提示；生产应使用受维护的 Node 版本并在升级前运行回归。数据库使用回滚日志 `DELETE`、`synchronous=FULL` 和外键检查，不依赖 WAL。该选择匹配当前低写并发单机目标，也避免假定旧 Node 内嵌 SQLite 已包含后续 WAL 修复。

数据库默认位于项目私有 `data/ttjf.sqlite`。`SQLITE_FILE` 可指定私有本地路径；不能放在公共 assets 或源码目录中。持久化目录不随代码升级删除，不使用网络共享盘，不运行 Node cluster 或多台应用服务器共享文件。若将来需要横向扩容，应重新评估存储，并做负载验证。

## 数据与并发契约

- 数据库仍是 SaaS 权威；数据库失败时返回错误，不改用浏览器或旧 JSON 文件记账。
- 每个操作从身份、会话和家庭权限检查，到状态更新、版本、授权消费和动作回执，处于同一事务。写事务在读取前使用 `BEGIN IMMEDIATE`；同连接的事务和独立查询排队，避免异步回调把请求混入别人的事务。
- 家庭状态、家长核验摘要、动作回执等以经过约束的 JSON 文本保存；时间以 UTC ISO 字符串保存。家庭业务日仍是上海，作物依然按实际时长成熟。
- 每个存续家庭在提交时必须恰有一个 owner。SQLite 延迟外键把家庭的 owner 指针绑定到 owner 成员，部分唯一索引保证最多一个；创建和交接必须在同一事务更新。不能通过删掉 PG 触发器而取消这个约束。
- 重试、版本冲突、限速、一次性授权、账号撤销、AI 在途租约和临时记录清理继续保留业务语义。PG 特有的行锁等待、跨实例锁调度和 schema 隔离不再是产品承诺。

## 升级与原数据

新 SQLite 文件由应用按版本初始化。只要仍有旧的 `DATABASE_URL`，即使同时设置 `SQLITE_FILE` 或容器注入默认路径，启动也会拒绝，避免静默建立看似丢失数据的新库。应先保存旧数据库和配置，再移除 `DATABASE_URL`、明确切换目标。这个 PR 不连接或修改任何实际 PostgreSQL 数据库。

已有 PG 用户应保留原版本、数据库和备份。当前私有家庭导出/导入工具可把一户的业务状态、家长核验摘要和回执导入新建空家庭，仍需明确已验证的所有者与目标，不迁移旧账号密码、会话或成员身份。完整账号级 PG→SQLite 自动导入不在本轮实现范围，不能宣称原库直接兼容。

## 备份与验证

整库备份使用 SQLite 一致性备份 API；恢复到不存在的新文件并验证完整性/外键，再配置服务使用恢复文件。应用数据、邮箱验证令牌与数据库备份均属于私有文件。详细命令见 [运行与数据操作](saas-operations.md)。

测试使用独立临时 SQLite 文件，不需要外部数据库；覆盖持久化重开、重复请求、授权消费、租户隔离、生命周期竞争、真实数据库故障回滚、备份恢复及浏览器消费链。原来只验证 PG 行锁/触发器/schema 的断言改为对应 SQLite 行为验证，业务断言保留。实际执行记录见 [v0.15 验证记录](sqlite-verification.md)；历史 v0.14 测试数字不计入本轮。

参考：[Node 22.17 SQLite API](https://nodejs.org/download/release/v22.17.0/docs/api/sqlite.html)、[SQLite 事务](https://www.sqlite.org/lang_transaction.html)、[SQLite 适用场景](https://www.sqlite.org/whentouse.html)。
